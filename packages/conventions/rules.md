## コード

- パッケージ・クレートの責務と依存は、README の構成の表に従う
- リポ内で共有するコードは `packages/*` に置く。リポをまたぐものは toolkit（npm の `@ryusenkei/*`）に置き、変更も toolkit で行う
- エントリポイントでは外部で使うものだけを公開し、他パッケージのものを公開し直さない
- テストは対象の近くに置く。言語ごとの置き方は `rules-ts.md`・`rules-go.md`・`rules-rust.md`
- テストで git を動かすときは、`GIT_DIR` などの git の環境変数を外す。フックから動くと、呼び出し元のリポを書き換える
- 依存の更新は Dependabot の PR で行う。月1回で自動の rebase はしないので、マージの前に手で rebase する
  - `package.json` に `"ryusenkei": { "dependabot": false }` を設定したリポでは、手元で `pnpm update` してまとめて更新する

## 設定と秘密値

- 秘密値はルートの `.env` にまとめ、配信は `pnpm env:push` だけで行う
- `*.tfvars` と Terraform の state はコミットしない
- `.env.example` に変数を足したら、`scripts/env.ts` の `targets` にも定義する。`scripts/env.ts` は `@ryusenkei/scripts` の `envCli` に配信先を渡すだけにする
- Cloudflare のトークンはデプロイ用と Terraform 用に分ける。CI でデプロイしないなら、どちらも GitHub に配信しない
- 環境変数を付けて実行するときは `node scripts/env.ts run NAME=value <cmd>` を使う。`NAME=value cmd` は Windows で動かない
- YAML の拡張子は `.yaml` にする（pnpm のファイルに合わせる）
- 共通ファイル（`.editorconfig`、`.github/dependabot.yaml`、`.claude/settings.json` など）は `@ryusenkei/conventions` から同期するので、直接編集しない。変えるときは toolkit で直し、`ryusenkei-conventions sync` で反映する

## 文章を書く場所

| 場所 | 性格 | 書くこと |
| --- | --- | --- |
| コード | 常に最新 | 意図は名前、型、関数の分け方で表す。コメントはその場所に欠かせない制約だけ |
| README | 変更と一緒に直す | 今の構成と設計の方針 |
| PR、issue | その時点の記録 | 経緯、検証、判断、採用しなかった案 |

- 決定の記録のファイル（ADR など）は置かない
- 個人名は書かない。コード、コメント、ドキュメント、設定値のすべてが対象

## 書く量

| 種類 | 書く | 書かない |
| --- | --- | --- |
| コードのコメント | 既定は書かない。書くのは、読み手が直そうとしてしまう一見おかしなコードの理由、コードから読み取れない外部の事実（仕様、プラットフォームの癖）、型で表せない単位や形式だけ | コードがしていることの説明、経緯、採用しなかった案、issue に結びつかない TODO |
| export の JSDoc | 名前と型以上の情報があるときだけ（単位、副作用、エラーコード、前提条件） | 名前を言い換えるだけの JSDoc |
| README | 何のリポか、動かし方、構成、今の設計の方針 | 経緯、判断の理由の長文、機能の宣伝 |
| PR | 背景（1〜3行）、レビューに要る粒度での変更、実際に行った検証 | 差分をなぞる説明、ファイルごとの実況 |
| issue | 問題、決めた範囲、未決の点。決まったら決定を書き足す | 調査の過程の全文 |
| コミットメッセージ | 1行で変更を言い切る | 本文での経緯の説明 |

説明が要ると感じたら、先にコードや構成を直せないか考える

## 書き方

- 語彙は慣例に合わせる。公式の文書の日本語訳や、業界でよく使う言い方を基準にし、安易に平易化や漢語化をしない
  - 例: データの操作は「作成」「取得」「更新」「削除」（UI と API の慣例）。ソフトウェアの版は「バージョン」
- 常体の短い文で書く。体言止めや、記号（`→`、`・`）で語をつなぐ略記にしない
- 表は比較や対応表のように、中身が表の形のものに使う。飾りとして表や、太字の見出しを付けた箇条書きにしない
- エラー、ログ、標準出力はコード（識別子）で表す。人が読む文言は表示のマスタ（辞書）から引き、その場に日本語を書かない
- コード上の値と環境変数はバッククォートで囲む。ドメインの概念、説明、表示の文言は日本語で書く
- 文章を見直すときは、日本語の文書・issue・PR に yomiyasu、英語の README に humanizer のスキルを使う（`.claude/settings.json` のプラグインで有効）。出てくるのは見直しの候補で、点数を合格の基準にしない
- prose-lint が止めるのは機械的な誤り（空白、句読点、表記の揺れ）だけ。ドメインの用語が表記の規則に当たるときは、`prose-lint.json` の `allow` に足す

## Git と PR

- add は変更・追加したファイルをパスで指定する。一括の add はフックで止まる
- push の前に `pnpm check` を通す。`check` を持つリポでは pre-push で強制される
- PR の本文は背景、変更、検証の順に書く
- 前の PR のブランチから PR を重ねた場合は、親のマージの後にスキル `stacked-pr` の手順で整理する
- マージは squash で、CI の全チェックの成功を確かめてから行う（フックで強制）
- epic のフロー（有効にしたリポだけ）
  - epic ごとに `dev/<issue の番号>-<内容>` を作り、sub-issue の PR は dev のブランチに向ける
  - dev のブランチへのマージに CI は使わず、pre-push の `pnpm check` を関門にする。チェックがある場合は成功が必要
  - `main` へのマージは、デプロイのときに dev のブランチからだけ行う。方法はほかの PR と同じ squash で、sub-issue ごとのコミットは sub-issue の PR に残る
  - デプロイの後も epic を続ける場合は、スキル `stacked-pr` の手順で dev のブランチを `main` から作り直し、開いている sub-issue の PR を載せ直す

## CI（GitHub Actions）

- CI は toolkit の再利用可能なワークフロー（`reusable-ci.yaml`、`reusable-pr-title.yaml`）を呼ぶ。リポ独自の検査は入力の `checks` に書き、言語ごとのジョブ（Go、Rust）は呼ぶ側に足す。呼び方は `@ryusenkei/conventions` の README

非公開のリポでは GitHub Free の時間を節約する（上限は組織の合計で月2,000分、ジョブごとに分単位で切り上げて計上）

- 実行するのは `main` 行きの PR だけ。マージの結果の ref は PR で検査済みなので、`main` への push では実行しない
- 検査は1つのジョブに順に並べる。並列に分けると、切り上げと準備の時間が増える
- 同じ PR で新しい実行が始まったら、古い実行を中止する（`concurrency` の `cancel-in-progress`）
- PR のタイトルの変更（`edited`）は、タイトルだけを検査する別のワークフローで扱う。依存は入れない
- キャッシュのキーにコミットの ID（`github.sha`）を含めない。毎回保存が走り、復元が効かなくなる
- Windows と macOS のランナーは公開のリポだけで使う。非公開では2倍と10倍で計上される
